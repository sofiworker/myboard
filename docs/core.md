# MyBoard 架构概览

> 版本：v1.0  
> 状态：Overview  
> 日期：2026-06-15  
> 定位：本文档只描述 MyBoard 的核心架构概念和模块边界，不定义具体实现逻辑、接口细节、JSON 结构或状态转移规则。  
> 实现标准：状态层以 `docs/orthogonal-state-management.md` 为唯一标准；输入引擎层以 `docs/engine.md` 为唯一标准；Android 平台桥接以 `docs/android-bridge.md` 为唯一标准；布局层以 `docs/layout.md` 为唯一标准。  
> ⚠️ **当前代码处于文档描述目标态的重构进行中**：本文档描述的是目标架构，并非现状快照。仓库中仍存在 `KeyboardState`、`KeyboardStateManager`、`LanguageSwitchManager`、`inputMethodId`、`arrangement` 等待替换的旧结构（详见 `docs/orthogonal-state-management.md` 第 2 节）。当文档与代码冲突时，以本文档及子文档描述的目标态为准，代码应按计划重构对齐。

## 1. 项目目标

MyBoard 是一款面向全球化输入、数据驱动布局和高度自定义体验的软键盘。它的核心目标是把输入法中容易互相耦合的语言、文字系统、输入方案、布局、候选、主题和扩展能力拆成清晰的层级，让新增语言、输入方案或布局时主要增加数据和资源，而不是不断复制业务代码。

核心设计原则：

- 状态唯一：运行时键盘状态必须来自统一上下文。
- 能力数据化：语言能力、输入方案、布局、字典和规则由数据描述。
- 逻辑分层：状态转移、输入引擎、布局渲染、字典候选、主题反馈互相解耦。
- 最小权限：只有具体能力被用户主动使用时才请求对应权限。
- i18n 完整：所有用户可见内容都必须支持国际化。

## 2. 正交状态矩阵

传统输入法常把“语言、模式、布局”做成链式关系，例如“中文输入法里的英文模式”或“日文输入法里的假名模式”。这种模型在多语言和混合输入场景下会快速失控。

MyBoard 使用正交状态矩阵描述输入语义：

- `Locale`：语境或语言区域，例如中文、中国大陆；英文、美国；日文、日本。
- `Script`：目标输出文字系统，例如汉字、拉丁字母、平假名、片假名、谚文。
- `Schema`：输入方案的稳定 ID，例如直接输入、拼音、双拼、五笔、罗马音、语音、手写；内置 Schema 可以提供常量，但不能做成限制扩展的固定枚举。

三者共同描述“当前用户希望用什么语境、输出什么文字、通过什么方案输入”。例如：

- 中文语境下输入汉字：`zh-CN + HANI + PINYIN`
- 中文语境下临时输入英文：`zh-CN + LATN + LATIN_DIRECT`
- 日文语境下输入平假名：`ja-JP + HIRA + ROMAJI`

状态模型和转移规则的完整实现以 `docs/orthogonal-state-management.md` 为准。

## 3. 动态语言能力

MyBoard 不在代码中硬编码“某个语言支持哪些文字系统、哪些输入方案”。语言能力由语言包声明，系统运行时注册和校验。

语言包描述的能力包括：

- 支持的语境。
- 支持的文字系统。
- 支持的输入方案。
- 默认输入状态。
- 使用的布局、引擎、字典、映射表或规则资源。

这种方式让新增语言或输入方案时优先增加语言包数据，而不是改状态机代码。状态层只理解通用概念和通用转移规则，不包含具体语言判断。

## 4. 输入引擎层

输入引擎层负责把输入事件转换为上屏文本、组合态或候选词。它不负责判断状态是否合法，也不负责切换语言、文字系统或输入方案。

MyBoard 的内置引擎按输入机制分类，而不是按语言分类：

- `DirectEngine`：直接上屏输入，适合英文、法文、德文及其他按键可直接映射为文字的语言。
- `TableComposingEngine`：编码查表输入，适合拼音、双拼、五笔、仓颉、郑码、注音等。
- `TransliterationEngine`：规则转写输入，适合日文罗马音、韩文谚文组合等。

不同语言和输入方案的差异通过映射表、编码器、有限状态机、字典和候选策略表达。输入引擎层的完整实现以 `docs/engine.md` 为准。

## 5. 数据驱动布局

键盘布局不承载输入法语义。布局只描述：

- 键位结构。
- 显示内容。
- 触发动作。
- 视觉和交互属性。

按键动作进入统一事件流后，由状态层和输入引擎层解释。这样同一个布局可以服务多个输入方案，同一个输入方案也可以换用不同布局。

布局系统应保持数据与视图分离，优先使用 Compose 渲染，并确保布局、按键、候选栏和工具面板都由统一状态驱动。

## 6. 字典与候选

字典和候选能力属于输入方案资源，不属于布局资源。一个输入方案可以声明使用哪份字典、候选排序策略、分页策略和选词策略。

字典层负责：

- 加载系统词典、语言包词典和用户词典。
- 根据输入引擎提供的查询码返回候选。
- 支持缓存和异步查询。
- 与 UI 和状态转移解耦。

候选栏只展示当前上下文中的候选快照，不直接查询字典，也不保存引擎 buffer。

## 7. Android 系统桥接

Android 的 `InputMethodSubtype` 无法直接表达 `Locale + Script + Schema` 的三维状态。MyBoard 将系统 Subtype 视为外部桥接入口，而不是内部状态源。

桥接原则：

- 系统切换进入 MyBoard 后，转换为正交状态请求。
- 内部状态变化后，可按需同步系统展示。
- 内部合法性仍由 MyBoard 的状态层决定。
- 外部语言包能力可以在 MyBoard 内部展示，不强依赖动态修改系统 Subtype。

## 8. 主题、反馈与扩展

主题系统以 token 为中心，把颜色、形状、字体、动效和反馈参数数据化。UI 组件只消费主题 token，不硬编码视觉值。

反馈系统统一处理：

- 触觉反馈。
- 声音反馈。
- 按键视觉反馈。
- 特殊输入模式反馈。

语音、手写、剪贴板、表情、符号、LLM 等能力都应作为独立功能层接入，通过统一状态和事件流与键盘主体协作。

## 9. 文档分工

本文档只作为架构总览，帮助理解系统为什么这样分层，以及各层之间如何协作。

具体实现以以下文档为准：

- `docs/orthogonal-state-management.md`：状态层唯一实现标准，覆盖 `KeyboardContext`、`LanguageManifest`、动态能力注册、状态转移和 Android Subtype 桥接。
- `docs/engine.md`：输入引擎层唯一实现标准，覆盖三大引擎族、`InputPipeline`、`InputSession`、编码器、字典、FSM 和候选策略。
- `docs/android-bridge.md`：Android 平台桥接层唯一实现标准，覆盖 `InputMethodService` 生命周期钩子映射、`EditorInfo`/`InputConnection` 收敛、`onUpdateSelection`、物理键盘、横屏 Extracted Text、`method.xml` 与权限封装。
- `docs/layout.md`：布局层唯一实现标准，覆盖 `LayoutDoc` 数据模型、5 种 `LayoutContainer` 测量、`LayoutEngine` 几何计算、`LayoutRegistry` 注册校验、`LayoutRenderer` 渲染、`ActionDispatcher` 正交动作派发、布局继承与 patch、候选/工具/键盘 region 组合、同一排列服务多 Schema 的全球化机制。

如果本文档与详细设计文档出现冲突，以详细设计文档为准。
